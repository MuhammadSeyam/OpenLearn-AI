المعمارية السحابية الكاملة — Online AI Architecture

No Local Models · API-Only · Multi-Provider Fallback

القرار الجوهري في هذا التقرير: لا نماذج محلية إطلاقاً. كل استدعاء LLM، كل embedding، كل OCR يتم عبر APIs سحابية لنماذج مفتوحة المصدر. هذا القرار له تبعات عميقة: لا حاجة لـ GPU، لا VRAM، لا Ollama، لكن في المقابل نحن رهائنون لـ rate limits وpricing وتوفر الـ providers. هذا القسم يقدّم التصميم الكامل لطبقة الـ AI مع شرح كل مكوّن وتدفّق البيانات.

لماذا API-Only هو القرار الصحيح لفريق طلاب؟

ثلاثة أسباب قاهرة: (1) تكلفة ثابتة منخفضة — لا GPU server بـ 200$/شهر، بل 20-50$/شهر APIs. (2) لا DevOps معقّد — لا إدارة CUDA، لا model loading، لا VRAM tuning. (3) scalability فوري — الـ provider يتوسّع تلقائياً، لا نحتاج نسخ خوادم. العيب الوحيد: الاعتماد على طرف ثالث — وهذا نعالجه بـ Multi-Provider Fallback.

1.3 شرح كل طبقة بتفصيل

AI Gateway (LiteLLM) — قلب المعمارية

الـ AI Gateway هو نقطة الدخول الوحيدة لكل استدعاءات الـ LLM. بدل أن نكتب adapter لكل provider، نستخدم LiteLLM — مكتبة Python مفتوحة المصدر توحّد الـ API لأكثر من 100+ provider. الفوائد: (1) كود واحد يعمل مع Groq و OpenRouter و Together وغيرها. (2) Automatic fallback عند فشل provider. (3) Cost tracking تلقائي. (4) Rate limit aggregation عبر providers. (5) Retry logic ذكي.

# مثال: استدعاء Qwen عبر LiteLLM مع fallback
from litellm import completion
response = completion(
    model="groq/qwen-2.5-7b-instruct",
    messages=[{"role":"user","content":"اشرح الانحدار اللوجستي"}],
    fallbacks=["openrouter/qwen/qwen-2.5-7b-instruct", "together-ai/Qwen/Qwen2.5-7B-Instruct"],
    api_key=...,
)
Provider Layer — متعدد المصادر

لا تعتمد على provider واحد. كل provider له نقاط ضعف: Groq rate limits صارمة، OpenRouter أبطأ، Together أحياناً يفشل، Cloudflare AI queue بطيء. الحل: قائمة providers مرتّبة حسب الأولوية لكل مهمة. مثلاً للـ Chat: Groq → OpenRouter → Together. للـ Embeddings: HuggingFace → Cohere → Voyage. الـ LiteLLM Router يحاولهم بالترتيب.

Prompt Layer — القاعدة الذهبية للـ Tokens

كل token يُكلّف مالاً. الـ Prompt Layer مسؤول عن: (1) Templates — لا تنسخ نفس الـ system prompt في كل طلب، استخدم template مُخزّن. (2) Prompt Compression — استخدم LLMLingua لضغط الـ prompt بنسبة 50% دون خسارة جوهرية في الجودة. (3) Few-Shot Library — أمثلة عربية مُختارة بعناية، تُضاف فقط عند الحاجة. (4) JSON Schema Enforcement — اطلب JSON صارم لتقليل post-processing.

Embedding Layer — الأرخص ممكن

Embeddings هي أكثر ما يُستهلك في النظام (آلاف chunks لكل PDF). الحل الأمثل: HuggingFace Inference API (مجاني جزئياً) مع BAAI/bge-m3. fallback إلى Cohere embed-multilingual-v3 (0.10$/1M tokens، free tier 1000 calls/شهر). تقنية التوفير الكبرى: cache الـ embeddings في Redis بـ key = hash(text). لنفس المادة، الـ embedding يُحسب مرة واحدة فقط.

Vector Search + Reranker

Qdrant Cloud — free tier 1GB (يكفي لـ ~100,000 chunks بـ 1024-dim). Hybrid search مدمج (Vector + BM25). للـ Reranker: Cohere Rerank free 1000 calls/شهر، أو Jina Reranker v2 (1M tokens free). عند تجاوز الـ free tier، استخدم Qdrant's built-in reranker (أقل دقة لكن مجاني).

Caching — لماذا هو حاسم؟

الـ caching يقلّل تكاليف الـ API بـ 30-60%. ثلاث طبقات: (1) Exact cache — hash(prompt) في Redis، TTL 24h. (2) Semantic cache — GPTCache يطابق prompts مشابهة دلالياً (تجاوز 90% similarity). (3) Embedding cache — لا تُعد حساب embedding لنفس الـ chunk. تقدير التوفير: 40-50% من استدعاءات الـ LLM، 80% من استدعاءات الـ embedding.

تفكيك مهام الـ AI — Task Decomposition

هل كل مهمة تحتاج LLM فعلاً؟

أكبر خطأ في مشاريع AI هو استخدام LLM لكل شيء. هذا يُكلّف mucho، يُبطّئ النظام، ويُدخّل hallucination لا داعي له. كثير من المهام يمكن حلّها بـ خوارزميات كلاسيكية أو embeddings فقط أو rules engine — بدون LLM إطلاقاً. هذا القسم يفكّك 15 مهمة في OpenLearn AI، وللأهمية: يحدّد أيها يستحق LLM وأيها لا.

المهمة تحتاج LLM؟ بدائل بدون AI Embeddings كافٍ؟ التعقيد Tokens/طلب التوصية
① Chat (RAG Q&A) نعم — لا (يحتاج generation) متوسط ~1500 LLM إجباري. Qwen 2.5 7B عبر Groq.
② Summaries نعم Extractive (TextRank) لا متوسط ~800 LLM للـ "exam summary". TextRank للـ "quick".
③ MCQ Generation نعم Templates + Cloze لا عالٍ ~2500 LLM ضروري للـ distractors ذكية.
④ True/False أحياناً Templates + sentence swap لا منخفض ~600 استخدم templates 70% + LLM 30%.
⑤ Fill-in-Blank أحياناً NER + Cloze deletion لا منخفض ~400 NER عربي (AraBERT) + LLM للـ polish.
⑥ Flashcards نعم Templates لا متوسط ~700 LLM للـ Q/A pairs عالية الجودة.
⑦ Exam Generation (CAT) أحياناً IRT + Item Bank لا عالٍ جداً ~0 (item selection) خوارزمية IRT. LLM فقط لتوليد أسئلة جديدة.
⑧ Knowledge Graph نعم NER + Rule-based لا عالٍ ~3000 LLM للـ relation extraction. NER للـ concepts.
⑨ Mind Maps أحياناً Hierarchical clustering نعم متوسط ~0 (embedding-based) Embedding clustering يكفي 80% من الحالات.
⑩ OCR لا (نماذج متخصصة) Tesseract/Surya لا متوسط ~0 (vision API) نماذج vision متخصصة (Surya) — لا LLM.
⑪ Image Understanding نعم (VLM) — لا عالٍ ~1200 VLM (Qwen-VL) لتفسير الرسوم. ميزة مؤجّلة.
⑫ Adaptive Recommendations لا Rules + BKT نعم (للـ similarity) متوسط ~0 خوارزميات deterministic + BKT. لا LLM إطلاقاً.
⑬ Difficulty Estimation أحياناً IRT + Flesch-Kincaid لا متوسط ~0 (formula) قراءة النص + IRT. LLM فقط للـ initial labeling.
⑭ Translation نعم Google Translate API لا منخفض ~500 NLLB-200 (مفتوح) أو Google Translate API.
⑮ Concept Extraction أحياناً NER (AraBERT) لا متوسط ~0 (NER model) NER للـ initial. LLM للـ expansion/disambiguation.
⑯ Learning Analytics لا SQL aggregations لا منخفض ~0 Queries SQL. لا AI إطلاقاً.
⑰ Student Modeling (BKT/IRT) لا Bayesian formulas لا متوسط ~0 صيغ رياضية صرفة. لا LLM إطلاقاً.
⑱ Spaced Repetition (SM-2) لا SM-2 algorithm لا منخفض ~0 خوارزمية Anki الشهيرة. لا AI.

2.2 أمثلة تفصيلية

مثال: Adaptive Recommendations بدون LLM

def recommend_next_concept(student_skm, kg, csp):
    candidates = [c for c in kg.concepts 
                  if c.mastery < 0.7  # ضعيف أو متوسط
                  and all(p.mastery > 0.5 for p in kg.prereqs(c))]
    
    score = lambda c: (
        0.4 * (1 - c.mastery) +             # حاجة
        0.3 * kg.unlocks_count(c) +          # قيمة المستقبل
        0.2 * forgetting_risk(c) +           # خطر النسيان
        0.1 * goal_alignment(c, csp.goals)   # توافق مع الأهداف
    )
    return sorted(candidates, key=score, reverse=True)[:3]
# تكلفة الـ tokens: 0$. زمن التنفيذ: 50ms.

3.2 التحليل التفصيلي لكل عائلة

Qwen 2.5 — الفائز العام للعربية

لماذا يفوز: Qwen 2.5 هو النموذج الوحيد في فئته (7B-72B) الذي يدعم العربية بجودة قريبة من GPT-4. مُدرَّب على 18 trillion tokens منها نسبة كبيرة من العربية. JSON output ممتاز (يدعم structured outputs natively). Tool calling مستقر. متاح على كل providers الكبرى.

الإصدارات الموصى بها: Qwen 2.5 7B Instruct (للـ chat العادي)، Qwen 2.5 14B (للـ MCQ)، Qwen 2.5 72B (للـ KG extraction المهم). التوفر: Groq (مجاني بـ rate limits)، OpenRouter ($0.15/M input)، Together AI ($0.20/M).

DeepSeek V3/R1 — ملك الـ Reasoning

لماذا مميز: DeepSeek R1 يتفوّق على GPT-4 في مهام الـ reasoning المجربة (MATH، GSM8K، MMLU). للأهداف التعليمية المتقدمة (إثبات نظرية، حل مسائل معقّدة)، لا منافس له في فئة الـ open-source. السلب: العربية أقل من Qwen بـ 2 نقاط. الـ API أبطأ (reasoing chain طويلة).

التوفر: OpenRouter ($0.55/M input)، DeepSeek official ($0.14/M input — أرخص 4x من OpenRouter)، Fireworks. الاستخدام في OpenLearn: صعوبة المسائل، توليد إثباتات، شرح خطوات الحل المعقّدة.

Llama 3.1 — الأكثر شعبية

الميزة: أكبر مجتمع، أكثر providers، استقرار أسطوري. متاح بـ speeds مذهلة على Groq (500+ tokens/s) و Cerebras (1000+ tokens/s). السلب: العربية جودة متوسطة. يكتب عربي لكن أحياناً بإيقاع إنجليزي، ويخلط LTR/RTL.

الاستخدام: المهام التي لا تحتاج عربياً عالي الجودة — paraphrasing، تصحيح الكود، استخراج البيانات.

Mistral — الخيار الأوروبي

الميزة: Mixtral 8x7B MoE — جودة عالية مع سرعة عالية. Mistral Nemo 12B خيار وسط ممتاز. السلب: العربية أضعف من Qwen وLlama. الـ JSON output متوسط الجودة.

التوفر: Together، OpenRouter، Cloudflare AI (مجاني!). الاستخدام: المهام الثانوية، الـ classification، الترجمة.

Gemma — محدود للعربية

المشكلة: Gemma 2 9B جودة جيدة للإنجليزية، لكن العربية ضعيفة (7/10). context قصير (8K) يمنع استخدامه للـ RAG مع PDFs طويلة. الاستخدام الوحيد الموصى به: المهام الإنجليزية البحتة (شرح كود، paraphrasing تقني).

Phi-3.5 — سريع لكن محدود

نماذج صغيرة (3.8B) سريعة جداً وبتكلفة منخفضة. السلب: جودة العربية منخفضة (5/10). لا يدعم tool calling بشكل مستقر. الاستخدام: مهام بسيطة جداً (classification، short answers).

OMo، Aya، SmolLM — لا للتشغيل السحابي

OLMo: fully open لكن العربية ضعيفة جداً (4/10)، context قصير، لا يدعم APIs تجارية. Aya: عربي ممتاز لكن رخصة CC-BY-NC تمنع الاستخدام التجاري. SmolLM: صغير جداً، غير مناسب للمهام التعليمية الجادة. التوصية: لا تستخدمهم في OpenLearn SaaS.

6.3 تقنيات خفض الـ Tokens (8 تقنيات أساسية)

① Prompt Compression (LLMLingua)

أداة LLMLingua من Microsoft تضغط الـ prompt بنسبة 50-70% دون خسارة جوهرية في الجودة. كيف يعمل: يحسب أهمية كل token ويحذف الأقل أهمية. التطبيق: اضغط الـ system prompt والـ context قبل الإرسال. التوفير: 40-60% من input tokens.

from llmlingua import PromptCompressor
compressor = PromptCompressor(model_name="bge-m3")
compressed = compressor.compress_prompt(
    original_prompt,
    rate=0.5  # احتفظ بـ 50%
)
# result: original 2000 tokens → compressed 1000 tokens

② Context Compression (RAG)

لا تُرسل كل الـ chunks للـ LLM. القاعدة: Top-5 chunks بعد re-ranking، كل chunk بحد أقصى 400 tokens. التوفير: 60-80% من input. التطبيق: بعد الـ retrieval، اقطع الـ chunks عند أقرب جملة كاملة.

③ Chunk Compression

كل chunk قبل الإرسال للـ LLM: (1) إزالة الـ headers/footers، (2) تطبيع المسافات، (3) إزالة الـ citations/references. التوفير: 20-30% من chunk size.

④ RAG Optimization (Smarter Retrieval)

كلما كان الـ retrieval أدق، قلّ عدد الـ chunks المطلوبة. التقنيات: Hybrid search (BM25 + Vector)، Cross-encoder reranking، Query rewriting. التوفير: 30-50% من الـ context tokens.

⑤ Caching (Exact + Semantic)

الأقوى: GPTCache للـ semantic caching. كيف: احسب embedding لكل query، ابحث عن query مشابه بـ cosine similarity > 0.92، أرجع الـ response المُخزّن. التوفير: 30-50% من استدعاءات الـ LLM. مثال: "ما هو الانحدار اللوجستي؟" و"عرف الانحدار اللوجستي" → نفس الإجابة من cache.

⑥ Conversation Memory (Sliding Window)

في الـ chat متعدد الـ turns، لا تُرسل كل الـ history. القاعدة: آخر 4 messages + ملخص (summary) للسابق. التوفير: 50-70% من input في الجلسات الطويلة.

⑦ JSON-Only Generation (Structured Outputs)

اطلب من الـ LLM JSON صارم بدل نص حر. الفائدة: (1) لا tokens ضائعة في الـ formatting. (2) لا حاجة لـ parsing. (3) validation فوري. التقنية: استخدم response_format={"type":"json_object"} في OpenRouter/Groq. التوفير: 15-25% من output tokens.

⑧ Streaming + Early Stopping

Streaming يُظهر الإجابة كلمة بكلمة. إضافة قوية: أوقف الـ generation عند اكتمال JSON أو الوصول لـ max_tokens محدّد. التوفير: 10-20% من output (إيقاف الإجابات الطويلة بلا داعٍ).

8.5 نقاط الفشل المحتملة

① Render Sleep Problem

Render free tier ينام بعد 15min من الخمول. أول طلب بعد النوم يأخذ 30-50 ثانية (cold start). الحل: استخدم UptimeRobot لـ ping كل 10 دقائق، أو انتقل لـ Railway ($5/month).

② Groq Rate Limits

Groq free يحدّ 30 req/min و 14K tok/min. عند ذروة الاستخدام (امتحانات)، قد يفشل الطلاب. الحل: Multi-provider fallback لـ Cerebras ثم Cloudflare AI.

③ HuggingFace Queue

HF free inference queue قد يأخذ 30-60 ثانية. غير مقبول لـ UX. الحل: استخدمه للـ background jobs (embeddings، OCR)، وليس للـ interactive chat.

④ Cohere Rerank Limit

1000 call/شهر فقط. سينفد بسرعة. الحل: استخدمه فقط للـ premium queries، وللـ default استخدم bge-reranker على HF.

⑤ R2 Storage Cap

10GB free. PDFs كبيرة قد تتجاوز. الحل: ضغط PDFs قبل التخزين، حذف المواد غير المستخدمة بعد 90 يوماً.

⑥ Neon Compute Hours

100 compute hours/شهر. قد ينفد عند الـ heavy queries. الحل: connection pooling، cache نتائج SQL في Redis.

الحقيقة القاسية

التشغيل بـ 0$ ممكن تقنياً لكنه هشّ. أيّ من: تجاوز rate limit، فشل provider، نمو سريع غير متوقع → تجربة مستخدم سيئة. التوصية: ابدأ بـ 0$ لـ MVP، انتقل لـ $20/شهر فور تجاوز 200 مستخدم. ميزانية $20 تحلّ 80% من مشاكل الـ free tiers.

  • Enterprise deals: 5 شركات × $500 = $2500/شهر.
  • إجمالي: $7500-15000/شهر.

10.4 المخاطر الحرجة لكل مرحلة

مخاطر P1 (مشروع التخرّج)

  • التأخير الزمني: قد يتجاوز 6 أشهر. الحل: نطاق صارم.
  • Bugs في العرض: الحل: اختبار الـ demo 20+ مرة.
  • اعتماد على طالب واحد: الحل: توثيق شامل.
  • فشل الـ free tier: الحل: قائمة providers بديلة.

مخاطر P2 (Beta)

  • Groq rate limits: قد تفشل في ذروة الامتحانات.
  • UX issues: قد يترك الطلاب بسبب البطء.
  • تسريب بيانات: بدون أمان كافٍ. الحل: JWT + rate limits.
  • انعدام الدعم: الطلاب يحتاجون مساعدة سريعة.

مخاطر P3 (إطلاق جامعي)

  • DB bottlenecks: 1000+ مستخدم يضغطون PostgreSQL.
  • تبعات قانونية: حقوق نشر PDFs المرفوعة.
  • دعم العملاء: يحتاج فريق (مطوّر + support).
  • انتقال المنصة: migration من free tiers.

مخاطر P4 (إطلاق عام)

  • cash flow: $1100/شهر قد يفوق الإيرادات.
  • scaling issues: 10K user يحتاج K8s.
  • churn rate: قد يصل 30% شهرياً.
  • منافسة: شركات كبرى قد تدخل السوق.
الخلاصة

الانتقال من 0$ شهرياً (مشروع تخرّج) إلى $1100/شهر (10K مستخدم) يستغرق 12-18 شهراً. كل مرحلة لها تمويلها الخاص — لا تحتاج استثمار خارجي حتى P4. القاعدة: لا تنتقل للمرحلة التالية قبل تحقيق إيرادات تغطي تكاليف المرحلة الحالية.

11.2 ما الذي سأعيد تصميمه اليوم؟

① إسقاط Neo4j نهائياً

في التقرير السابق، أبقيت على Neo4j كـ "optional". اليوم: أحذفه نهائياً من التصميم. PostgreSQL + JSONB + recursive CTEs يكفي لـ KG حتى 100K عقدة. أي إشارة لـ Neo4j تضيف تعقيداً لا داعي له.

② إسقاط LangChain فوراً

التقرير السابق اقترح "الاستبدال التدريجي". اليوم: لا تستخدم LangChain إطلاقاً من اليوم الأول. LiteLLM + httpx مباشرةً. وفّر 50% من الـ latency، تجنّب الـ bugs.

③ إسقاط Kubernetes حتى 10K مستخدم

التقرير السابق اقترح K8s في "Stage 3". اليوم: Render / Railway حتى 5-10K مستخدم. K8s overhead هائل (محوّلات DevOps، Helm، monitoring). ليس لفريق 2-4 طلاب.

④ إسقاط Multi-Region حتى 50K مستخدم

Single region (Frankfurt أو Virginia) يكفي حتى 50K MAU. Multi-region يضاعف التكلفة والتعقيد.

⑤ إسقاط Celery Beat للحظة الـ MVP

جدولة المراجعات يمكن أن تتم بـ cron job بسيط على Render. لا حاجة لـ Celery Beat حتى 1000 مستخدم.

⑥ إسقاط DeepSeek R1 من MVP

التقرير السابق اقترح DeepSeek R1 لـ "Math/Logic". اليوم: Qwen 2.5 7B يكفي لـ 95% من الحالات. DeepSeek R1 مكلف وبطيء. أضِفه فقط كـ Premium feature لاحقاً.

⑦ إسقاط "100 توصية" — ركّز على 20

100 توصية = شلل تحليلي. التركيز على 20 توصية فقط (Tier 1 + Tier 2) يحقق 90% من الفائدة.
